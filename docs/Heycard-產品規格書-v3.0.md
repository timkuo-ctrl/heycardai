## 1. 產品定義

Heycard 是**數位名片 ＋ AI 人脈情報**，不是電子名片工具。三層結構：

| 層 | 內容 |
|---|---|
| 名片 | 五種金屬材質的數位名片，支援多重身分、多語言版本 |
| 人脈 | 拍照收錄他人名片，AI 自動分類、補公司情報 |
| 情報 | 洞察：AI 告訴你「今天該找誰、說什麼」，**每一條都附可執行的下一步** |

**產品的勝負點**（所有設計決策從這裡推）：

> 勝負不在名片好不好看，在**收完名片之後有沒有事情發生**。
> 每次打開都要有「一件為你準備好的事」——IG 是新貼文，Heycard 是「今天該找誰」。

**商業模式**：Free → Plus（NT$79/月）→ Pro（NT$179/月），年繳送 NFC 實體卡。**付款在網頁完成，不經 App Store。**

## 3. 系統架構與技術決策

### 3.1 原型與正式版的關係

原型為單一 HTML（909KB），純 vanilla JS、無框架、localStorage 儲存。**這是規格載體，不是要移植的程式碼。** 正式版請依下列決策重寫。

### 3.2 必須從第一天就做對的決策

| REQ-ID | 決策 | 理由 |
|---|---|---|
| ARCH-01 | **i18n 一律 key-based**（`t('key', {params})`），不得用「渲染後比對字典替換」 | 原型用的是渲染後翻譯，已補到約 900 條仍無法 100%；句子用字串相接組成時字典永遠查不到。key-based 讓漏譯在結構上不可能發生，也是加日文韓文的前提 |
| ARCH-02 | **句子不得用字串相接組成**，一律用帶參數的模板 | 同上。`'上次你記下的是「' + note + '」'` 這種寫法無法翻譯 |
| ARCH-03 | 產品介面文字與用戶自填內容**在資料層就分離** | 見 §N |
| ARCH-04 | AI 生成內容（訊息草稿、提案）**以介面語言直接生成**，不得事後翻譯 | 草稿是要送出去的東西，翻一半比不翻更糟 |
| ARCH-05 | 所有 AI 判讀的輸入與門檻**可設定**，不得寫死在畫面邏輯裡 | 規則表要能隨市場調整（見 §F 時機） |

## 6. 功能規格

### A. 註冊與登入

| REQ-ID | 規格 |
|---|---|
| A-01 | Email ＋ 6 碼 OTP 註冊。密碼 8 碼以上含英數 |
| A-02 | **OTP 必須 10 秒內送達。** 等待畫面顯示「已寄出，通常 10 秒內」，30 秒後提供「改用密碼」 |
| A-03 | OTP 輸入自動跳格，退格回上一格 |
| A-04 | 🆕 註冊完成後立即執行「待領人脈」兌現（見 I-06） |
| A-05 | 🆕 若註冊前碰過未開通的 NFC 卡，註冊完成後自動進入綁定（見 J-03） |

### B. 名片建立

| REQ-ID | 規格 |
|---|---|
| B-01 | 兩種方式：拍實體名片 / 自己輸入。兩者都可，之後隨時能改 |
| B-02 | 只有姓名是必填 |
| B-03 | 🆕 **拍攝流程：正面 → 反面 → 辨識。** 反面可略過 |
| B-04 | 🆕 **相機自動判斷橫向／直向。** 演算法：每 300ms 取樣一幀 → 邊緣偵測找名片矩形 → 長寬比 ≥1.2 判橫向、≤0.83 判直向 → 去抖動 → 偵測前預設橫向 → 使用者可按「旋轉」永久覆蓋 |
| B-05 | 🆕 拍完後必須有明確的結果帶：狀態（正面拍好了）＋ 為什麼要拍反面 ＋ 滿版主行動。**不可只給兩顆並排小按鈕** |
| B-06 | OCR 後**只讓用戶確認三個欄位**（姓名、公司、手機），其餘可留空；信心低的欄位以琥珀色標記 |
| B-07 | 🔴 OCR 準確度決定第一印象，辨識錯字會讓用戶覺得整個 App 不可靠。需要真實名片測試集驗收 |

### C. 多重身分

| REQ-ID | 規格 |
|---|---|
| C-01 | 一個帳號可有多張名片，代表不同身分 |
| C-02 | 交換、收錄、分享都使用「目前使用中」那一張 |
| C-03 | 分享時可選「只給這一張」或「給完整檔案（對方可自己切換）」 |

### D. 名片設計

| REQ-ID | 規格 |
|---|---|
| D-01 | 卡片幾何：`H = round(w × 1.586)`；縮放 `k = w/320` |
| D-02 | 五種材質：Silver / Steel / Manganese / Aurora / Mist。顆粒 `feTurbulence baseFrequency=.85 numOctaves=4`，`mix-blend-mode:overlay` |
| D-03 | **付費選項可試不可帶走**：付費樣式可即時預覽在自己名片上，按儲存時才要求升級。免費部分照常存檔 |
| D-04 | 全站只有一個升級面板 `upsell(need, why)`，永遠顯示「現在 → 升級後」的用戶自己的名片 |
| D-05 | 重複的 SVG 漸層 id 會互相污染，重複渲染的卡片必須用純色或動態 id |

### E. 人脈

| REQ-ID | 規格 |
|---|---|
| E-01 | 列表顯示：頭像、姓名、身分行、活資訊行 |
| E-02 | 🆕 **Heycard 用戶 vs 非用戶要一眼看見，而且是「好感」不是「標籤」**：用戶頭像加錳→青漸層細環、名字旁勾勾、右側可直接按的訊息鈕；非用戶灰階字首磚 ＋ 箭頭 |
| E-03 | **非用戶不是資料少的人，是資料不會更新的人。** 掃名片就要有登記資料、產品、同事數 |
| E-04 | 公司情報：T0（登記資料）**3 秒內顯示**，較慢的（官網摘要）非同步補上，卡片先出骨架 |
| E-05 | 合作機會：**沒有交集就誠實說沒有**（PRIN-08）。免費層必須保留公司情報與合作機會 |
| E-06 | 備註是 AI 配對的燃料，系統不得覆蓋用戶寫的備註 |

### F. 洞察（Pro）

結構：**時機 → 本週變化 → 你的網路 → 引路人 → 判斷 → 互相**

| REQ-ID | 規格 |
|---|---|
| F-01 | **每一區塊、每一條都必須以可點的下一步結尾**（PRIN-09） |
| F-02 | 建議埋點 `insight_next_step_clicked{section}`，此為 Pro 續訂的先行指標 |
| F-03 | **時機**：規則表 × 使用者專長 × 人脈條件。規則表須可設定（ARCH-05） |
| F-04 | 🆕 **時機的相關性硬門檻**：`fit` = 使用者名片的 offer/industry/title/headline 是否接得上這一波的受益方清單 → **接不上就完全不顯示**。再乘以符合人數（0 位也可顯示，但 CTA 改為「發需求」）與時效權重（1 / 0.7 / 0.4） |
| F-05 | 🆕 每張時機卡右上角顯示「因為你的『X』」晶片（PRIN-07） |
| F-06 | 🆕 名片沒填 offer/industry 時**不猜**，顯示引導卡 |
| F-07 | 🆕 **引路人用圖示磁磚，不用文字說明**：3 欄、環形頭像、姓名、公司簡稱、三種圖示徽章（👑決策層 / 🔑唯一窗口 / 🔍正在找人）＋ 引薦鈕 ＋ 底部圖例（PRIN-01） |
| F-08 | 「你的網路」維度切換**就地重繪**，不整頁重整、不跳回頂端 |
| F-09 | 🔴 時機規則是台灣商業節奏。go global 時每個市場需自己的規則表（美國 Q4 是財年末、日本 4 月是年度始）。**須先設計「地區」欄位** |

### G. 尋求與推薦

| REQ-ID | 規格 |
|---|---|
| G-01 | 發需求前先在自己人脈裡找，此步驟沒有別人看得到 |
| G-02 | 推薦流程：推薦 → 對方看到引薦卡（只有姓名、公司、職稱與推薦理由）→ 兩邊都同意才交換名片 |

### H. 訊息

| REQ-ID | 規格 |
|---|---|
| H-01 | AI 開場三種寫法，可再修改 |
| H-02 | 🔴 **對方回覆時必須推播。** 第一次被回覆是留存的關鍵事件；沒有回覆通知，AI 開場就只是自言自語 |

### I. 公開頁與陌生訪客 🆕

| REQ-ID | 規格 |
|---|---|
| I-01 | **四條入口，同一畫面，脈絡不同**：`?c=<id>&via=qr` / `&via=link` / `&via=search` / `?nfc=<卡號>`。頂部脈絡列顯示對應說明 |
| I-02 | 訪客看到的欄位由卡主的公開設定決定。**預設保守**：姓名／職稱／公司／一句話／網站公開；手機、Email、地址**預設不公開** |
| I-03 | **搜尋引擎收錄為勾選制，預設關。** 未開啟時從搜尋進入顯示「這一頁沒有開放搜尋」，但持有連結／條碼／實體卡者仍可看 |
| I-04 | ⚠️ **`cardHTML()` 會把物件上每一個欄位印在卡面上。任何要給訪客看的名片渲染，一律先過欄位遮蔽（`pubCard`），不得直接傳原始物件。** 原型曾發生欄位清單正確但卡片圖像洩漏手機與地址 |
| I-05 | **訪客主行動是「把名片寄到我的 Email」**，不是註冊。先把他真正想做的事做完，不擋路。註冊為次要輕推 |
| I-06 | 🆕 **Email 種子迴圈**：訪客留下的 Email 記入待領池；日後他用**同一個 Email** 註冊時，存過的每一張名片自動進入他的人脈，並顯示「你的人脈不是空的」。**這是解決冷啟動的關鍵機制** |

### J. NFC 實體卡 🆕

| REQ-ID | 規格 |
|---|---|
| J-01 | **卡綁帳號，不綁單張名片。** 可指定代表身分、隨時更換 |
| J-02 | **一張卡兩個生命週期**：未開通 → 卡主在開卡；已開通 → 別人在碰你的卡 |
| J-03 | 未開通 ＋ 已登入 → 直接進綁定；未開通 ＋ 未登入 → 記住卡號 → 進註冊 → 註冊完自動綁定 |
| J-04 | 已開通 ＋ 他人感應 → 進入卡主公開頁（訪客模式）；卡主自己感應 → 進入管理 |

### K. 多語言名片 🆕

| REQ-ID | 規格 |
|---|---|
| K-01 | **主要版本由本人自填，永不翻譯。** 第二／三／四語言由 AI 起草 |
| K-02 | **一律走「草稿 → 逐欄確認 → 發布」。** 未發布只有本人看得到 |
| K-03 | **姓名一律不機器翻譯。** 非母語版使用名片上的「英文名」欄位；未填則擋住發布 |
| K-04 | **公司名只用登記的英文名**（接商業司），不是翻譯結果 |
| K-05 | 職稱給候選，不自動選定。AI 沒把握的欄位**留白**，不硬猜 |
| K-06 | 電話、Email、網站各語言共用，不重複輸入。留白欄位在該語言版本不顯示 |
| K-07 | 訪客端依瀏覽器語言自動挑版本，另一版永遠一鍵可見 |
| K-08 | 主推兩種語言（母語 ＋ 英文）。**第二語言是選項不是義務**——美英市場一種即可 |
| K-09 | **多語言為免費功能**，不列入付費層 |

> **為什麼不收費**：台灣紙本名片本來就是雙面雙語，B-03 拍到的正是這兩份。雙語不是加值功能，是被數位化的實體物件本來的形狀。且一張外國人讀不懂的名片在人脈圖裡是死路——收費等於替自己的網路效應設上限。

| N-03 | ⚠️ N-02 的實作必須在**資料層**分離（ARCH-03）。原型用 `translate="no"` ＋ 值比對兜底，仍有邊界情況：若用戶職稱剛好叫「設計」，介面上的「設計」按鈕也會停止翻譯 |
| N-04 | 語言架構照 IG／FB：預設跟裝置走不問人；設定 → 語言為一頁清單，第一項「裝置語言（預設）」；未上線語言灰掉標「即將推出」 |
| N-05 | Web 額外吃網址參數 `?hl=en` |
| N-06 | 🆕 **中英排版分家。** 不得翻譯完沿用同一組字體度量：<br>· 中文方塊字無升降部 → 行距 1.75，字級維持<br>· 英文有升降部 → 小字級需更鬆行距，但字數多故字級收半級<br>· 英文標題 `text-wrap:balance`、內文 `text-wrap:pretty`（中文不需要）<br>· 英文全大寫微標籤加字距（中文加了反而鬆散） |
| N-07 | 🆕 **說明句長度上限：英文 60 字。** 實測全站英文長句已從 112 條降到 6 條 |
