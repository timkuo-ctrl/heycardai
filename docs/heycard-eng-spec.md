# 1. 產品範圍

## 1.1 一句話定義

Heycard 是**數位名片 ＋ AI 人脈情報**的行動應用。用戶建立自己的名片、拍下別人的名片、系統自動為每張名片長出情報，並在累積人脈後提供 AI 分析與對外的個人公開網頁。

## 1.2 v1 範圍界線

| 做 | 不做（v2 之後） |
|---|---|
| iOS ＋ Android App | 平板／大螢幕專用版式 |
| 中英雙語（zh-TW / en） | 其他語系 |
| 淺色為基準 ＋ 深色衍生 | — |
| Email OTP ＋ 密碼登入 | 社群登入（Google / Apple Sign In）❓ |
| 個人版 IAP 訂閱 | 年費方案 ❓ |
| 企業版官網訂閱 ＋ 後台 | 企業版 SSO |
| 個人公開網頁（付費） | 自訂網域 |
| 無障礙：字級縮放 ＋ 對比 | 完整 VoiceOver 支援 |
| 實體 NFC 卡（申請流程） | 聚會模組 ❓ |

**明確不收手機號碼**（帳號層級）。名片上的電話是名片欄位，與帳號無關。

# 2. 技術需求

## 2.1 平台

| 項目 | 需求 |
|---|---|
| iOS | 最低版本 ❓（建議 iOS 16+，涵蓋率與 SwiftUI 成熟度平衡） |
| Android | 最低版本 ❓（建議 API 26 / Android 8） |
| 公開網頁 | 伺服器端渲染（SSR）**必要** — 見 `PUB-08` SEO/GEO |
| 企業後台 | Web，桌機優先，最小寬度 1280px |

## 2.2 SSR 是硬需求，不是選項

個人公開網頁的**唯一付費理由之一是被 Google 與 AI 引擎索引**。純 client-side render 的 SPA 會讓這個賣點失效。公開網頁必須：

- 伺服器輸出完整 HTML（姓名為 `<h1>`，非圖片、非 canvas）
- 輸出 `schema.org/Person` 與 `schema.org/Organization` JSON-LD
- 輸出 OG meta ＋ 動態產生的 OG image

## 2.3 離線能力

| 功能 | 離線行為 | REQ |
|---|---|---|
| 人脈庫 | **可讀**（本地快取） | `SYS-01` |
| 拍名片 | **可拍，佇列上傳** | `SYS-02` |
| AI 情報 | 不可用，顯示快取版本 ＋ 「離線中」標記 | `SYS-03` |
| 其他 | 顯示離線狀態 | `SYS-04` |

# 4. 核心元件

## 4.1 名片元件 `<BusinessCard>`

這是整個產品的核心元件，**必須做成單一元件、參數化**，不可各畫面各寫一份。

### Props

| Prop | 型別 | 說明 |
|---|---|---|
| `material` | `silver \| steel \| manganese \| aurora \| mist` | 材質，5 選 1 |
| `width` | number | 卡寬，**所有內部尺寸依此等比縮放**（基準 320px） |
| `density` | `0 \| 1 \| 2` | 精簡／標準／完整，依填寫欄位數自動判定 |
| `photo` | boolean | 有無大頭貼 |
| `orientation` | `portrait \| landscape` | App 內直式；OG image 橫式 |
| `data` | CardData | 見 §6.2 |

### 縮放公式

```
k = width / 320
任何尺寸 = round(基準值 × k × 100) / 100
高度 H = round(width × 1.586)      // 直式
高度 H = round(width / 1.586)      // 橫式
```

### 四個簽名元素（缺一不可）

1. **巨大超細姓名**：字重 200、字距 −5.5%、佔卡面上半部
2. **錳紫斜線**：緊接姓名，`skewX(-16°)`，底部對齊姓名基線
3. **底部三點**：`Hey — to — Connect`，6.5px（320 基準），字距 .24em，兩端對齊
4. **右上角同色壓印 Logo**：`currentColor`，透明度依材質（銀卡 `rgba(25,26,28,.17)`）

### 材質定義

每個材質是一組五個值：`bg`（線性漸層）、`sh`（高光放射漸層）、`ink` / `sub` / `mut` / `line` / `mark`（文字與線條色）、`slash`（斜線色）、`gr`（顆粒透明度）。

**顆粒層**：`feTurbulence` fractalNoise，`baseFrequency=0.85`，`numOctaves=4`，去飽和，`mix-blend-mode: overlay`，透明度深色 `.13` / 淺色 `.07–.09`。

> 金屬的真實感來自**表面粗糙度**，不是反光。不要用明暗交替做假鉻感。

### 硬性規則

| 規則 | REQ |
|---|---|
| 卡片**一律正放，禁止 3D 傾斜**（`rotateY` / `rotateX`） | `CARD-01` |
| 姓名**不隨密度縮小**，只有底部資訊區長出來 | `CARD-02` |
| 空欄位**不留佔位**，直接收合 | `CARD-03` |
| 縮圖尺寸（< 110px）**不顯示大頭貼** | `CARD-04` |
| 大面積使用時漸層必須另調柔化版（見 §4.2） | `CARD-05` |

### 驗收

**每一種材質都必須在「3 種密度 × 有無大頭貼 × 深淺兩版」共 12 種組合下都成立。** 這是名片元件的完整驗收矩陣。

## 4.2 頁面尺度的卡片語言（公開網頁專用）

公開網頁的頁首**不放卡片物件**，而是把卡片語言放大到整頁。

| 元素 | 桌機 | 手機 |
|---|---|---|
| 側邊留白 | 48 | 22 |
| 大頭貼 | 80 圓形 | 58 |
| 姓名 | 60 / 200 | 40 |
| 錳紫斜線 | 8 × 52，`skewX(-16°)` | 5.4 × 34 |
| 英文名 | 12 / 300，字距 .34em，全大寫 | 9.5 |
| 職稱 · 公司 | 14（職稱 500 / 公司 300，中間 3px 圓點） | 12 |
| 主張句 | 19 / 400，最大寬 470 | 14 |
| Hey to Connect | 9，字距 .26em，透明度 .30，兩端對齊 | 8 |
| 頁首總高 | 約 620 | **≤ 430**（確保連結露出第一屏） |

**⚠️ 大面積漸層必須另調。** 卡片那組五段高反差是為 320px 小物件調的，直接放大會在中段出現髒塊。頁面版：

```css
linear-gradient(158deg,#FDFDFE 0%,#F4F4F6 26%,#E3E3E7 56%,#EDEDF0 80%,#F9F9FA 100%)
```

❓ **姓名過長**：60px 適用四字中文名。五字以上或英文長名會折行。需定自動縮級規則（建議 60 → 52 → 44），**不可讓它折行**。

## 4.3 連結列 `<LinkRow>`

| Prop | 說明 |
|---|---|
| `platform` | `web \| book \| ig \| yt \| li \| line \| fb \| shop \| custom` |
| `title` | 顯示名稱 |
| `url` | 真實網址，**必須顯示** |
| `featured` | boolean，主要連結用大卡 |

| | 主要（featured） | 次要 |
|---|---|---|
| 排法 | 整列 | 桌機雙欄／手機單欄 |
| 圖示 | 42px | 34px |
| 標題 | 14 / 600 | 12.5 / 600 |
| 箭頭 ↗ | 錳紫 | `#B4B4BE` |
| 最小列高 | — | **56px** |

**五條硬規則**

1. `LNK-01` 永遠顯示真實網址（`hongcheng.com.tw`）
2. `LNK-02` 每一列都有 ↗，標示會離開本頁
3. `LNK-03` 圖示用平台辨識色，**只上 8% 淡底**（`{brand}14`），圖形全彩
4. `LNK-04` 列高 ≥ 56px（Apple HIG 建議 44pt，本產品拉到 56）
5. `LNK-05` 手機一律單欄

## 4.4 區塊標題 `<SectionTitle>`

15px / 600 / `color-ink`，右側一條 1px `#EAEAEE` 延伸到容器邊界。

> 這條線不是裝飾，是**橫向結構樑**。移除它版面重量會塌。

## 4.5 按鈕

| 變體 | 樣式 |
|---|---|
| Primary | `linear-gradient(150deg,#7E7DFF,#5C5CFF)`，白字，陰影 `0 7px 18px rgba(92,92,255,.32)` |
| Secondary | 白底，`color-ink`，面板陰影 |
| Tertiary | `#F4F4F7` 底，`1px solid #E8E8ED` |
| Accent-soft | `#F0F0FF` 底，`#DDDDFF` 框，`#4A4AE0` 字 |

尺寸：`padding 12px 22px`，字 13.5 / 600，圓角 12。最小點擊區 **44 × 44pt**。

❓ 未定義：hover / press / disabled / loading 四態的具體數值。建議 press 為 `scale(0.97)` ＋ 亮度 −6%，disabled 為透明度 .4 ＋ 不可點。

# 5. 資訊架構

## 5.1 主導覽（5 分頁）

```
人脈 🔔  ｜  尋求人脈  ｜  ⦿ 拍攝／掃描  ｜  訊息  ｜  我的名片 ⚙
```

| 規則 | REQ |
|---|---|
| 中央為**凸起主按鈕**，錳紫 | `NAV-01` |
| 通知鈴鐺在**人脈頁右上**，不佔分頁 | `NAV-02` |
| 設定在**我的名片頁右上齒輪** | `NAV-03` |
| AI 儀表板是**人脈頁的第二個檢視**（頂部切換「人脈 / 洞察」），不新增分頁 | `NAV-04` |
| AI 對話是**訊息列表置頂的第一個對話**，取消全域浮動按鈕 | `NAV-05` |
| onboarding 後落地於**人脈** tab | `NAV-06` |

## 5.2 搜尋框 —— AI 的第二道門

`SRCH-01` 搜尋框 placeholder：**「搜尋，或直接問我一句話」**

`SRCH-02` 輸入判定：
- 關鍵字（無空格短詞、可比對欄位）→ 就地比對人脈庫，即時結果
- 自然語言（含問句、動詞、超過 N 字）→ **自動轉進 AI**，並帶入當前 context

❓ 判定門檻未定義。建議：含問號、或字數 > 8、或含動詞 → 判為自然語言。需實測。

`SRCH-03` AI 回答**直接輸出可行動的人脈卡**（含推薦理由），下方給後續動作按鈕。

### 🚩 `AUTH-10` 是系統性風險，請優先處理

系統代寄的邀請信若被大量檢舉，會拖垮同網域的 OTP 送達率，**直接癱瘓註冊（R2）、OTP 登入（L3）與忘記密碼（L4）**。

要求：
- 交易信（OTP、密碼重設）：獨立網域，如 `mail.heycard.com`
- 邀請信：另一網域，如 `invite.heycard.com`
- 邀請信以**邀請人具名**寄送，含「不再接收」連結且退訂即時生效
- 設每人每日寄送上限 ❓（數值未定）
- v1 邀請只做 Email，不做簡訊

### 企業 Email 處理 `AUTH-20`

`login_email`（帳號）與 `card_email`（名片顯示）**資料分離**。註冊時依 Email 網域分三種情境：

| 情境 | 判定 | UI |
|---|---|---|
| A | 免費信箱（gmail/yahoo/hotmail…） | 「這是你的個人信箱」＋ `[ + 新增公司信箱 ]` 就地展開 |
| B | 自訂網域 | 「✓ 看起來這是你的公司信箱」＋ `改用其他信箱` — **零操作通過** |
| C | OCR 抓到 Email | 名片上的為權威值 |

用 chip 呈現，不用「?」按鈕。微文案固定：**「登入帳號不會改變」**。
一般用戶不驗證公司信箱；**加入企業團隊時才要求網域驗證**。

## 7.6 INTEL — AI 情報層（免費）

這是產品的第二支柱。**核心原則：分層填入，每一層到位就填，絕不整卡空白等待。**

```
拍完名片 → OCR 完成 → T0（0 秒）→ T1（數秒）→ T2（背景）
```

| 層 | 延遲 | 資料來源 | 內容 | 完成行為 |
|---|---|---|---|---|
| **T0 即時** | **0 秒**，不需外部查詢 | 名片資料 ＋ 使用者自己的人脈庫（本地） | 純規則推導 | 立即渲染 |
| **T1 快查** | 數秒 | 公司登記公示資料 | 統編等登記欄位 ＋ 關聯公司 | **覆蓋 T0 的產業初判** |
| **T2 深度** | 背景非同步 | 爬取 ＋ LLM | 公司簡介、產品服務、新聞 | 標示「已更新」或推播 |

### `INTEL-01` T0 必須豐富到「就算 T1／T2 全部失敗，情報卡也不難看」

這是硬性要求，不是目標。T0 全部由本地規則產生，零外部依賴。

### `INTEL-02` 職級判定表（職稱關鍵字 → 層級）

| 層級 | 關鍵字 | 呈現字串 |
|---|---|---|
| 決策層 | 董事長、執行長、總經理、CEO、Founder、負責人 | **決策層** · 通常握有預算與最終決定權 |
| 高階主管 | 副總、協理、VP、處長 | **高階主管** · 有部門預算權、可影響決策 |
| 中階主管 | 經理、總監、Director、Manager | **中階主管** · 有執行決定權，通常是實際窗口 |
| 專業／執行 | 專員、工程師、顧問、Specialist | **專業職** · 影響者／使用者，非決策者 |

⚠️ **需建完整中英文職稱對照表**，處理台灣常見寫法（協理、副總經理、特助…）。這是一張要人工建的表，不是演算法，請排入工。

### `INTEL-03` 職能判定（9 類）

業務／行銷／技術研發／生產製造／採購／財務／人資／法務／經營管理
呈現：**業務職能** · 適合談合作與通路

### `INTEL-04` 產業推斷

以「公司名稱關鍵字 ＋ 職稱」先給初判 → **T1／T2 到位後以權威資料覆蓋**。覆寫是明確規則，不是選項。

### `INTEL-05` 人脈庫內部關聯（本地查詢，三種聚合）

| 類型 | 輸出字串 |
|---|---|
| 同公司 | 「你已經認識這家公司的 2 個人」 |
| 同產業 | 「這是你第 7 位科技業人脈」 |
| 同場域 | 「同一場活動你還認識了 3 個人」 |

版面規則：放在 T0 區塊**最後收尾**。

### `INTEL-06` T1 欄位

統一編號、公司全名、資本額、成立日期、**代表人**、營業項目、登記地址、營業狀態

🌟 **關聯公司**：同一代表人或董事名下的其他公司。
呈現：「代表人 王大明 同時擔任 3 家公司負責人」＋ 清單

### `INTEL-07` T2 欄位

公司簡介、主要產品服務、近期新聞／募資／獲獎、官網與社群、規模估計

### `INTEL-08` 查無資料的誠實原則

**「永遠不要空白，永遠不要假裝知道。」**

查無資料時直接顯示「這是一家新公司／目前尚無公開資料」—— **這本身就是情報**。同時仍需補上 T0 全部項目 ＋ T1 登記資料（新公司通常仍有統編、成立日期、代表人）。

### `INTEL-09` 高價值線索組合規則

```
若 公司成立年份為新 且 代表人名下有其他公司
→ 產生組合洞察
```
範例輸出：「這是一家 2025 年成立的新公司，但代表人 周思齊 另有 2 家公司」

### `INTEL-10` 多身分情報基準

```
若 對方有多張名片 → AI 情報一律以「他給你的那張」為準
```
否則產業分類與公司登記查詢會錯亂。

### `INTEL-11` 職涯異動衍生洞察（零外部資料成本）

對方換公司後自動計算兩件事，並附在通知裡：
1. 你在他的**舊公司**是否還有其他人脈
2. 他去了新公司 → 你多了一個新公司的入口

### `INTEL-12` 群體洞察資料量門檻

| 人脈數 | 可成立的分析 |
|---|---|
| 1 | 單人情報卡（T0–T2） |

# 8. 狀態機與邊界情況

設計檔：`heycard-states.html`（12 畫面 ＋ 24 列對照表）

## 8.1 三種空狀態，處理方式不同

| 類型 | 意義 | 呈現 |
|---|---|---|
| **首次空** | 還沒開始用 | 插圖 ＋ 一句期待 ＋ **主要行動按鈕** |
| **篩選空** | 有資料但這個條件沒有 | 一行字 ＋ **清除條件**，不放插圖 |
| **結果空** | 搜尋不到 | 一行字 ＋ **建議的下一步**（如「改用 AI 問問看」） |

> ⚠️ 常見錯誤：三種都用同一個大插圖。篩選空放大插圖會讓用戶以為資料不見了。

## 8.2 三種錯誤嚴重度

| 嚴重度 | 呈現 | 用在哪 |
|---|---|---|
| **可自行恢復** | inline 提示 ＋ 重試按鈕 | 載入失敗、上傳失敗 |
| **需要用戶決定** | 對話框 ＋ 兩個明確選項 | 合併衝突、覆蓋警告 |
| **系統性** | 全頁狀態 ＋ 客服入口 | 斷網、伺服器錯誤、強制更新 |

## 8.3 逐頁狀態需求

| 頁面 | 0 筆 | 載入中 | 失敗 | 離線 |
|---|---|---|---|---|
| 人脈庫 | 首次空 ＋「拍下第一張名片」 | 骨架屏（列表 5 列） | 重試 | **可讀快取**，頂部橫幅 |
| 洞察 | 「再收 3 張就能看到分布」 | 骨架屏 | 重試 | 顯示快取 ＋ 時間戳 |
| 情報卡 | T0 永遠有內容 | T1/T2 逐層填入，**不整卡 loading** | 該層顯示「暫時取不到」 | 顯示已快取層 |
| 訊息 | 首次空 | 骨架屏 | 重試 | 唯讀 |
| 尋求人脈 | 官方示範貼文（**標示為範例**） | 骨架屏 | 重試 | 唯讀 |

# 13. 隱私、資料界線與合規

## 13.1 資料界線判準（可直接轉成欄位白名單）

**主判準：你在場的事可以講，你不在場的事不要講。**
判定式：這筆資料是不是**你也參與產生**的？

| ✅ 可顯示 | ❌ 不可顯示 |
|---|---|
| 你們 2025/03 在台北國際電腦展認識 | 他總共有 480 位人脈 |
| 你們共同認識 3 個人（那 3 人也在你人脈庫） | 他上週跟 12 個人交換過名片 |
| 他換公司了（**認識之後**） | 他的名片這個月被看了 200 次 |
| 他在你人脈庫中的分群位置 | 他 3 年換過 4 份工作（含認識前） |

## 13.2 對稱性原則（實作規則）

**A 看得到關於 B 的什麼事實，B 就必須看得到關於 A 的同一項。**

| 類別 | 例子 | 是否需雙向 |
|---|---|---|
| **事實** | 共同人脈、認識時間與場域、職涯異動、驗證標記 | **必須雙向** |
| **分析與筆記** | 高潛力標記、AI 建議、個人備註、分類標籤 | 單向無妨 |

因此資料模型需有欄位區分**事實**與**分析**兩類。

### 明確禁止實作

| 禁止 | 理由 |
|---|---|
| 「查看誰看過我的名片」 | 單向觀察，情蒐原型 |
| 「只有付費用戶看得到共同人脈」 | 付費用戶單向觀察免費用戶，違反對稱性 |

付費的 AI **分析**不受對稱性限制（「王大明是高潛力夥伴，建議這樣開場」對方看不到，不算違反）。

## 13.3 透明度頁

`PRIV-01` 設定內須有一頁「**你的人脈看得到你什麼**」，逐項列出會被已交換者看到的資訊。

## 13.4 App Store 上架必要條件

| # | 項目 | 狀態 |
|---|---|---|
| R1 | App 內刪除帳號入口 | ✅ 已規格（`AUTH-11`） |
| R2 | UGC 檢舉／封鎖／人工審核 | ✅ 已規格（`SEEK-09`） |
| R3 | IAP 架構 | ✅ 已規格（`PAY-01`） |
| R4 | 電子發票 | ✅ 個人版由 Apple 開；企業版自行開 |

| R7 | 年齡分級 | ✅ 依平台分級 |

## 13.5 🔴 R6 的範圍（需法務）

條款必須明確涵蓋，缺一不可：
